# 题库插图：格式与显示路径（设计评估稿）

> 2026-10-21 更新：题库插图仍未实现；同一套 `stb_image` + 纹理缓存路线已先用于
> 首页背景，见 [`主页背景设计.md`](主页背景设计.md)。

> 目标：题库里能带图片，刷题页面（题干、材料、解析、选项）能显示。
> 现状：题库是**单文件纯文本**；题干/材料只按字符串排版；界面是软件光栅化 ImGui
> （图标已经是位图纹理，`ImGuiRenderer` 里有纹理管理，这条路是通的）。

## 1. 先看约束（决定了方案怎么选）

| 约束 | 说明 |
| --- | --- |
| 单文件导入导出 | 现在导入收一个 `.quiz`、导出也只有一个文件；SAF 那边是「选一个文件」 |
| 纯文本可手写 | 格式刻意像 INI，用户会手改；图片不能把文件弄成二进制垃圾 |
| 两端都能读 | Windows：`assets/banks` 或 `data/banks`；Android：APK 内 assets 或 `files/banks` |
| 软件渲染 | 没有 GPU 纹理管线，但图标已经走「解码 → 纹理 → ImGui::Image」这条路 |

## 2. 三种格式方案

### A. 同目录图片 + 相对路径（推荐先做）

```ini
[q]
id = q1
stem = 下图是哪种结构？
image = images/q1.png
image = images/q1-detail.png   # 可以多张
image_caption = 图 1：结构示意  # 可选，跟上一张对齐
```

- 题库文件所在目录旁边有一个 `images/`；路径**只允许相对**（拒绝 `..`、绝对路径、URL）。
- 优点：格式最干净、可 diff、可手改；图片独立缓存（改一张图不用动题库）；解码/显示都简单。
- 缺点：**题库不再是单文件**——导入要连目录一起拿，分享要打包。这正是它的主要成本。

### B. 内嵌 base64（单文件自包含）

```ini
[image]
id = fig1
format = png
data = iVBORw0KGgoAAAANSUhEUg...
```

- 优点：单文件继续成立，导入/导出/分享一行代码都不用改。
- 缺点：体积 ×1.33、不可读不可 diff、手写几乎不可能、解析要一次性解码整段（大图会吃掉几 MB 内存）。
- 适合当**兜底**（比如用户非要只发一个文件），不适合当主格式。

### C. `.axbank`（zip 容器，本质是 A 的打包形态）

```
bank.quiz
images/q1.png
```

- 优点：自包含 + 压缩；分享一个文件；内部仍是 A 的相对路径写法。
- 缺点：读写要走 zip（miniz 单头文件可以），导入/导出要多一条分支；文件名后缀/识别也要加。
- 我的建议：**A 做地基，C 做分享形态**（导出时如果有图片就打成 `.axbank`，没图片仍然是 `.quiz`）。

## 3. 显示路径（从文件到屏幕）

1. **模型**：`Question` / `Material` 各加 `std::vector<std::string> images`（+ 可选 caption）。
2. **解析**：`[q]` / `[material]` 里认 `image =`（多行累加），路径做安全校验；导出原样写回。
3. **读字节**：`platform` 补一个「读二进制」接口（Windows 读文件 / Android 读 `AAsset`），
   现在只有 `readTextFile`。
4. **解码**：接 **stb_image**（单头文件、PNG/JPEG/BMP，MIT）。两条路都省了（不用 WIC + BitmapFactory 各写一套）。
5. **纹理**：复用 `ImGuiRenderer` 现有的纹理表；缓存 key = `题库id + 相对路径 + mtime/大小`，
   避免每帧解码。大图要先按显示宽度降采样（一张 2000×1500 解码后 12MB）。
6. **排版**：
   - 第一期：图片**单独成块**，画在题干卡片下方 / 材料正文下方，按可用宽度等比缩放；
     卡片高度要把图片高度算进去（现在 `wrappedTextHeight` 只算文字）。
   - 第二期：行内插图（`stem = 如图 [img:q1] 所示`）——要把文本和图片拆段自绘，工作量明显更大。
7. **交互**：点图放大（弹窗）；加载失败显示「图片缺失：路径」（别让整题空白）。

## 4. 工作量评估

| 子任务 | 估时 | 风险 |
| --- | --- | --- |
| 解析 `image =` + 模型 + 导出往返 | 0.5 天 | 低 |
| 二进制读文件（两端）+ stb_image 接入 | 0.5 天 | 低 |
| 图片渲染（题干/材料下方，等比缩放，卡片高度） | 0.5–1 天 | 中：高度测量、滚动区 |
| 纹理缓存 + 内存上限 + 失败占位 | 0.5 天 | 中：大图 |
| 导入导出携带图片（zip / 目录授权） | 1–2 天 | **高**：SAF 目录授权、打包、兼容 |
| 行内图文混排（第二期） | 1–2 天 | 高：自绘排版 |

- **MVP（A 方案 + 单独成块 + 导出暂不携带图片）≈ 2–3 天**；
- **完整（A + `.axbank` 导入导出）≈ 4–6 天**；
- 如果只做 B（内嵌 base64）：显示链路 ≈ 1.5 天，但题库文件会变丑、变大。

## 5. 建议的落地顺序

1. 解析 + 模型 + 导出（纯文本层，先把手写格式定下来）；
2. 二进制读取 + stb_image + 纹理缓存（先只支持 Windows，能截图验证）；
3. 题干/材料下方渲染图片（等比缩放、点击放大、缺失占位）；
4. Android 走通（assets 里的图片 + `files/banks/images`）；
5. 导入导出：有图 → `.axbank`（zip），无图 → 仍 `.quiz`；
6. 二期再做行内图文混排。
